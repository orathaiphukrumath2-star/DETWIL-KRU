# DETWIL 0.3: สมัครสมาชิกและหลายบทบาท

สมาชิกสมัครด้วยชื่อ อีเมล และรหัสผ่านที่ตั้งเอง ไม่จำเป็นต้องมีบัญชี Google ไม่ส่ง OTP หรืออีเมลยืนยันอัตโนมัติ **อีเมลเป็นชื่อเข้าสู่ระบบ ไม่ใช่อีเมลที่ระบบพิสูจน์เจ้าของแล้ว** ผู้ดูแลต้องยืนยันตัวบุคคล/สังกัดก่อนอนุมัติบทบาท

## เส้นทางใช้งาน

1. สมาชิกเปิด `/register` กรอกข้อมูล เลือกขอบทบาทได้หลายรายการ และเลือกโรงเรียนสำหรับบทบาทระดับโรงเรียน
2. บัญชีเริ่มเป็น PENDING เข้าสู่ระบบเพื่อตรวจสถานะหรือขอบทบาทเพิ่มได้ แต่ยังสร้างผลงานหรือดูงานผู้อื่นไม่ได้
3. ผู้ดูแลเข้าสู่ `/studio` เลือกบทบาท “ผู้ดูแลระบบ” แล้วเปิด “โรงเรียนและบัญชีผู้ใช้” เพื่อตรวจคำขอและอนุมัติทีละบทบาท
4. สมาชิกกดตรวจสถานะล่าสุด จากนั้นเลือกบทบาทที่ใช้งานด้านบน เช่น ครูของโรงเรียน ก หรือผู้ตรวจของโรงเรียน ข
5. ในบทบาทครู เลือก “สร้างชุดผลงาน” เพิ่มแผนการสอน สื่อ และหลักฐาน แล้วบันทึก/เผยแพร่/ส่งตรวจตามระบบเดิม

ถ้ารายชื่อโรงเรียนยังว่าง สมาชิกสมัครบัญชีไว้โดยไม่เลือกบทบาทได้ ผู้ดูแลเพิ่มโรงเรียนจริงก่อน แล้วสมาชิกขอบทบาทภายหลัง หรือผู้ดูแลเพิ่มบทบาทให้โดยตรง ไม่มีการสร้างโรงเรียนสมมติระหว่างสมัคร

## สิทธิ์หลายบทบาท

ใช้ตาราง `USER_ROLES` เดิม หนึ่งแถวต่อหนึ่งบทบาทและหนึ่งขอบเขต:

| RoleCode | ScopeType | ScopeID |
| --- | --- | --- |
| TEACHER | SCHOOL | SchoolID ของโรงเรียน |
| SCHOOL_ADMIN | SCHOOL | SchoolID ของโรงเรียน |
| SUPERVISOR | GLOBAL | DETWIL |
| AREA_ADMIN | GLOBAL | DETWIL |
| SUPER_ADMIN | GLOBAL | DETWIL |

สถานะ PENDING, ACTIVE, REJECTED, REVOKED; ใช้ StartDate/EndDate เพื่อกำหนดช่วงสิทธิ์ได้ ผู้สมัครขอ SUPER_ADMIN เองไม่ได้ หน้าจอสมาชิกไม่อนุญาตสร้างหรือถอน Super Admin

หนึ่งคนมีบทบาทต่างโรงเรียนได้โดยขอเพิ่มแยกครั้ง สถานะอนุมัติเป็นรายบทบาท ไม่ใช่อนุมัติทั้งบัญชีแล้วให้สิทธิ์ทุกคำขอ สมาชิกสลับได้เฉพาะบทบาทที่อนุมัติ อยู่ในช่วงเวลา และโรงเรียนยังเปิดใช้งาน

`USER_ROLES` เป็นแหล่งสิทธิ์จริง ไม่ใช้ `USERS.PrimaryRole` เพียงอย่างเดียวอีกต่อไป PrimaryRole เป็นบทบาทตั้งต้น/ข้อมูลประกอบ และยังใช้ตรวจเจ้าของในฟังก์ชันตั้งค่าที่รันจาก Apps Script Editor

เพิ่มคอลัมน์ `ActiveRoleID` ท้าย `AUTH_SESSIONS` โดยไม่ลบคอลัมน์หรือ session เดิม จำนวนชีตยังเป็น 29 ชีต ฟังก์ชันอัปเกรด `DETWIL_prepareMembershipSystem` ตรวจ prefix หัวตารางก่อนเพิ่มคอลัมน์ หากไม่ตรงจะหยุด ไม่เขียนทับ

คำขอแต่ละครั้งตรวจบัญชี session บทบาท และโรงเรียนจากชีต ไม่เชื่อ role/UserID ที่ client ส่งมา ไม่รวมสิทธิ์ทุกบทบาทเข้าด้วยกันโดยอัตโนมัติ ผู้ตรวจโรงเรียนหนึ่งจึงไม่ใช้สิทธิ์อีกโรงเรียนในโหมดเดียวกัน เมื่อถอนสิทธิ์ บทบาทที่เลือกไว้จะหยุดใช้กับคำขอถัดไป ไม่เงียบแล้วกลับมาให้สิทธิ์จาก PrimaryRole

## รหัสผ่านและการจำบัญชี

สมาชิกตั้งรหัสผ่านเองและใช้รหัสเดิมเข้าสู่ระบบได้ ความยาว 12–128 ตัวอักษร ไม่บังคับรูปแบบซับซ้อนหลายเงื่อนไข จึงใช้วลีที่จำง่ายได้ **ชีตไม่เก็บรหัสผ่านตัวจริง และผู้ดูแลเปิดอ่านรหัสเดิมไม่ได้** ตามแนวทาง [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

สมาชิกใหม่ใช้ Node.js scrypt บน Vercel (N=131072, r=8, p=1) ผูกกับอีเมลมาตรฐาน ก่อนส่ง proof ไปยัง Apps Script ซึ่งเติม random salt และ pepper ตามระบบ hash เดิม เก็บ PasswordAlgorithm=SCRYPT_SHA256_V1, PasswordHash และ PasswordSalt ไม่เก็บ proof โดยตรง ไม่เปลี่ยน pepper เดิม

บัญชีเก่า SHA256_ITERATED_V1 ยังเข้าสู่ระบบได้ด้วยรหัสเดิม การล็อกอินผ่านเว็บใหม่สำเร็จจะยกระดับการเก็บเป็น SCRYPT_SHA256_V1 อัตโนมัติ ไม่บังคับรีเซ็ตรหัสผ่าน อีเมลผูกกับ proof จึงไม่ควรแก้ Email ในชีตเองโดยไม่ตั้งรหัสใหม่

ตัวเลือก “จำการเข้าสู่ระบบ 30 วัน (อุปกรณ์ส่วนตัว)” เก็บเฉพาะ session cookie แบบ HttpOnly/Secure/SameSite ไม่เก็บรหัสผ่านใน localStorage หรือชีต หากไม่เลือก session อายุ 8 ชั่วโมง ทั้งสองแบบหมดอายุคงที่ ไม่ขยายเองทุกครั้งที่เปิดหน้า การออกจากระบบเพิกถอน session ฝั่งหลังบ้านด้วย

ลืมรหัสผ่านสมาชิก: ผู้ดูแลตั้งรหัสชั่วคราวให้ผ่านหน้าจอ สมาชิกต้องเปลี่ยนก่อนใช้ข้อมูล การตั้งรหัสชั่วคราวหรือเปลี่ยนรหัสจะเพิกถอน session เดิมทั้งหมด ไม่ส่งอีเมลเพื่อประหยัดโควต้า Super Admin ไม่ถูกรีเซ็ตรหัสผ่านผ่านหน้าสมาชิกนี้ การกู้ Super Admin ที่ลืมรหัสยังต้องใช้บัญชี Google เจ้าของและขั้นตอนที่ควบคุมจาก Apps Script

## ลดโควต้า Google

- ไม่ใช้ Google Sign-In หรือ MailApp/GmailApp ใน flow สมัครสมาชิก จึงไม่ส่งเมลยืนยัน/OTP
- คำขอ API ส่วนตัวที่ไม่มี cookie ถูกปฏิเสธที่ Next.js ก่อนเรียก Google
- รายชื่อโรงเรียนและตัวเลือกสมัครผ่าน `/api/membership` แคช browser 60 วินาที และ CDN 5 นาที จึงอาจรอไม่เกินรอบแคชก่อนเห็นโรงเรียนที่เพิ่งเพิ่ม
- งาน scrypt ทำบน Vercel ไม่ทำบน Apps Script และการจำ session ช่วยลดการตรวจรหัสผ่านซ้ำ
- หน้าสมาชิกไม่มี polling ตรวจสถานะตลอดเวลา สมาชิกกดรีเฟรชเมื่อผู้ดูแลอนุมัติแล้ว

**ไม่ได้หมายความว่าไม่ใช้โควต้า Google เลย** การสมัคร บันทึก อ่านชีต ตรวจสิทธิ์ และไฟล์ Drive ยังอยู่ใน [โควต้า Apps Script](https://developers.google.com/apps-script/guides/services/quotas) ไม่ได้ load test 1,000 คนพร้อมกัน

มี throttling ฝั่ง Vercel แบบ in-memory สูงสุด 20 auth attempts ต่อ IP ต่อ 10 นาทีต่อ instance และ honeypot ในฟอร์ม เพียงช่วยลดการยิงซ้ำ ไม่ใช่ distributed rate limiter/CAPTCHA แบบป้องกัน bot ได้สมบูรณ์ อาจต้องปรับเมื่อหลายคนใช้เครือข่าย/IP โรงเรียนเดียวกัน และ direct Apps Script endpoint ยังเป็น public ควรเพิ่มมาตรการ anti-abuse ก่อนประชาสัมพันธ์วงกว้าง

## ผลตรวจ

Unit tests 35 กรณีและ production build/TypeScript ผ่าน รวมสมัครซ้ำ, ไม่ให้สมัคร Super Admin, เก็บ hash, ไม่มีอีเมล, รออนุมัติ, หลายบทบาท/ข้ามโรงเรียน, ถอน/หมดอายุสิทธิ์, session 30 วัน, เปลี่ยน/รีเซ็ตรหัสและเพิกถอน session, schema migration และอัปเกรดบัญชีเดิม

ยังต้องทดลองสมัครและอนุมัติด้วยบัญชีจริงของผู้ใช้ การทดสอบอัตโนมัติใช้ fixture ในเครื่อง ไม่ได้สร้างบัญชีตัวอย่างหรืออนุมัติสิทธิ์สมมติในชีต production
